# Explorer Application Architecture

## Overview and Purpose

Explorer is a **modular visual framework** for communicating energy forecast data generated by Generator and served by the API. It is designed to be easily customizable by developers while providing professional-quality visualizations for end users.

**Design Principles**:
- **Modularity**: Components can be added, removed, or replaced without breaking the application
- **Developer-friendly**: Clear structure, well-documented, easy to fork and customize
- **User-focused**: First page is an introductory report with text, charts, and maps
- **Professional output**: Charts and visualizations suitable for presentations and reports
- **Responsive**: Works seamlessly on mobile, tablet, and desktop screens
- **Transparent**: Data assumptions and sources explained without overwhelming users

The `:::Component{props}` directive syntax is transformed into Svelte components by `src/lib/remark/directivePreprocess.js`; see CLAUDE.md for the MDsveX gotchas and how to opt into the `reports` layout.

**Component Organization**:

See `/explorer/src/lib/components/` for the current component tree. Key groupings:

- Chart components at the top level (`AreaChart.svelte`, `Histogram.svelte`, `TimeLine.svelte`, `SegmentBars.svelte`, etc.) — all wrap LayerChart primitives.
- `map/` — Mapbox GL wrapper (`Map.svelte`, `MapBox.svelte`, `Legend.svelte`, `Popup.svelte`, `YearSelect.svelte`) plus `PersistentDesktopMap.svelte` which keeps the desktop map mounted across route changes.

- `navigation/`, `layout/`, `report/` — page chrome and report-specific UI.

## Component Standardization

All chart components follow standardized patterns for consistency, maintainability, and developer experience.

**TypeScript Interface Standard**:
- All components implement interfaces from `/explorer/src/lib/types/ChartComponent.interface.ts`
- Base interface: `BaseChartProps` (data, loading, error, geography, year, scenario, class)
- Specialized interfaces: `TimeSeriesChartProps`, `GeographicChartProps`, `SectorChartProps`

**Data Loading Pattern (Hybrid)**:
- Components accept `data` as props from parent
- If `data` is null/empty, component fetches its own data
- Use `$effect()` to trigger fetch when parameters change
- Always include loading states and error handling

**Map Component Data Loading**:
The Map component has specific data requirements:
- `geojsonData`: GeoJSON FeatureCollection with county polygons (always required)
- `yearData`: Demand data for all geographies (optional - will fetch if not provided)
- `scenario`: Scenario object (required for fetching data)

**Best Practice**: Pre-fetch `yearData` in page loaders for better performance and reliability:
```typescript
// In +page.ts loader
const geoQuery = makeDemandQuery({
    start: String(year),
    end: String(year + 1),
    resolution: '1Y',
    aggregation: 'sum',
    geography: 'all',    // All geographies
    segment: 'total',
    scenarioId
});
const geoData = await fetchDemandData(geoQuery, fetch);

// Pass to Map component
<Map
    geojsonData={geojson}
    yearData={geoData}
    year={year}
    scenario={scenario}
    ...
/>
```

**Shared UI Components**:
- `LoadingSkeleton` - 4 variants (chart, map, table, text)
- `ErrorState` - Consistent error display with retry functionality
- `EmptyState` - Unified no-data messaging

**Container Query Support**:
- All standardized components use `@container` class for container-aware responsiveness
- Tailwind config includes `@tailwindcss/container-queries` plugin
- Components respond to their container width, not viewport width

## Responsive Design System

**Breakpoint Strategy**:
- **Mobile-first approach**: Base styles for mobile, progressively enhance for larger screens
- **Tailwind breakpoints**: `sm:` (640px), `md:` (768px), `lg:` (1024px), `xl:` (1280px), `2xl:` (1536px)
- **Container queries**: Use for component-level responsive behavior
- **Grid layouts**: Responsive grid with `grid-cols-1 md:grid-cols-2 lg:grid-cols-3` patterns

## Content Management System

Explorer uses a markdown/MDsveX-based content system so narrative text lives outside component code. Content files sit at `/explorer/src/content/{locale}/{section}/*.{md,svx}`; today only `sv/` is populated (`pages/`, `reports/`).

**Key pieces**:
- `src/lib/contentLoader.ts` — loads files via Vite glob, resolves by slug + locale, caches results.
- `src/lib/components/content/ContentShell.svelte` — the reusable page wrapper used by thin route files (`<ContentShell slug="pages/about" />`).
- `src/lib/components/content/MarkdownLayout.svelte` and `ReportLayout.svelte` — MDsveX named layouts. Opt into the reports layout with `layout: reports` in a `.svx` file's frontmatter.
- `src/lib/remark/directivePreprocess.js` — Svelte preprocessor that transforms `:::Component{props}` syntax into `<Component>` with auto-imports. Runs before MDsveX. This is used instead of `remark-directive` because MDsveX 0.11.x bundles an old unified version (see CLAUDE.md for details).

Simple pages live as `.md` with directive syntax; pages with loops/icons/state stay as `.svx`.

**Key Development Practices**:
- Use `$effect()` for reactive side effects (not `onMount()` when already using `$effect()`)
- Components accept data as props OR fetch their own data (hybrid pattern)
- Always include loading states and error handling
- Test responsiveness at multiple breakpoints
- Document complex data transformations
- Keep components under 300 lines (split if larger)
